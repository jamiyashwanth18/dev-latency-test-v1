<!-- sdlc:auto:start overview -->
Dev latency test - v1 is a small-team leave management app generated by the Quorq AI SDLC platform, built as two separate applications in one repository: a Vite + React 19 single-page frontend whose screens were reviewed and approved and currently render seeded sample data, and a FastAPI 0.115 backend with SQLAlchemy 2.0 models, Alembic-managed PostgreSQL 16 schema (with a local SQLite fallback), that so far only exposes a health-check endpoint, with business-logic routers to be added one at a time as the architecture is approved.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js (for npm, Vite, React 19 tooling)
- Python 3.12
- pip
- Docker and Docker Compose (for the local PostgreSQL 16 service)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. Clone the repository.
2. Copy .env.example to .env and set the variables described in backend/README.md / ENVIRONMENT.md.
3. From the repo root, run `docker-compose up -d` to start the local PostgreSQL 16 database (optional: the backend falls back to a local SQLite file if DATABASE_URL is not set).
4. cd backend && pip install -r requirements.txt
5. cd backend && uvicorn app.main:app --reload  (this applies Alembic migrations and seeds platform accounts on startup)
6. In a separate terminal: cd frontend && npm install
7. cd frontend && npm run dev
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend routers are added one per architecture component as endpoints are implemented, and included from app/main.py; unimplemented endpoints return a typed StubResponse rather than failing.
- Pydantic request/response models in schemas.py are named after the entities in the approved data model.
- SQLAlchemy models use dialect-neutral types (e.g. Uuid, JSON.with_variant for jsonb) so the same models run against PostgreSQL in production and SQLite locally.
- The database schema is only ever changed through Alembic migrations in backend/migrations; app.database.run_migrations() applies them automatically on startup.
- Fixed value sets (Role, LeaveType, LeaveStatus, NotificationType) are modeled as StrEnum classes stored by value.
- All environment variables are read once through app.config.get_settings(), each with a local default so the app runs without a .env file.
- Startup seeding of platform accounts (seed.py) is idempotent: a user is created only if none with that email already exists.
- Frontend screens live one per file under src/screens/, each approved independently.
- Frontend shares a common component/icon vocabulary (src/lib/ui.tsx, src/lib/icons.tsx) and brand tokens (src/lib/brand.ts, index.css) across screens.
- Frontend API access is centralized in src/lib/api.ts (apiFetch, bearer-token handling); screens currently render seeded sample data rather than calling it.
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| Frontend requests to the backend are blocked by CORS. | Set ALLOWED_ORIGINS on the backend to the frontend's origin(s), comma-separated; it defaults to the Vite dev server's origins. |
| No PostgreSQL server available locally. | The backend falls back to a local SQLite file (./app.db) when DATABASE_URL is unset; alternatively run `docker-compose up -d` to start the PostgreSQL 16 service from docker-compose.yml. |
| `pytest` fails with an import error for `app`. | Run pytest from the backend/ directory; backend/pytest.ini sets pythonpath = . so `import app` resolves. |
| Frontend builds and deploys but breaks at runtime from a type mismatch. | Run `npm run typecheck` (tsc --noEmit) before shipping; `npm run build` bundles without type checking. |
| Playwright e2e run can't boot the backend. | Ensure the backend's dependencies are installed into backend/.venv (per backend/README.md), since playwright.config.ts starts the API via backend/.venv/bin/python. |
<!-- sdlc:auto:end troubleshooting -->
