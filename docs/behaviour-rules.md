# Behaviour rules

How this app behaves where the requirements and the API contract do not say. QA's
tests and the code both follow these rules. The platform keeps this file: the first
rules come from the contract and the code, and each later rule from a decision made
when a test and the code disagreed.

- Sign-in is POST /sessions with {user_id} of an existing active user and needs no token, no password and no other field; it returns {token, user:{id, full_name, role}, expires_at} with a 128-char-max opaque random token (at least 32 characters) that is unique across the sessions table and is never a JWT or derivable from the user id.
- POST /sessions with a user_id that does not exist, is malformed, or belongs to a deactivated user returns 404 {"detail": "..."} and creates no session row.
- Signing in again does not end earlier sessions: each POST /sessions adds a new row, so a user may hold several valid tokens at once and each is revoked only by its own sign-out or by deactivation of that user.
- Sessions use a sliding inactivity window: every successful authenticated request sets last_active_at to now and extends expires_at to now plus the configured idle lifetime (SESSION_IDLE_MINUTES, default 60 minutes), so a session only expires after that long with no requests.
- DELETE /sessions/current sets revoked_at on the calling session and returns 204 with an empty body; calling it again with the same token returns 401, and a revoked or expired token is never reusable.
- Any request to a protected endpoint without an Authorization header, with a non-bearer scheme, or with a token that is unknown, revoked or past expires_at returns 401 with body {"detail": "Not authenticated"} and no WWW-Authenticate-driven redirect.
- A token belonging to a user whose is_active was set false is rejected with 401 on the next request, because PATCH /admin/users/{id} setting is_active=false stamps revoked_at on all of that user's sessions in the same transaction.
- A caller who is authenticated but whose role or reporting line forbids the action (any /admin/* endpoint for a non-HR/Admin, deciding on a request that is not the caller's direct report's) returns 403 {"detail": "..."} and changes nothing.
- A path {id} that is a well-formed UUID but matches no row, and a path {id} that is not a valid UUID at all, both return 404 {"detail": "..."}; resources owned by another user that the caller may not see (another user's notification) also return 404 rather than 403.
- Invalid or missing request-body fields return FastAPI's default 422 with {"detail": [{"loc": [...], "msg": "...", "type": "..."}]}, including end_date earlier than start_date, an empty or whitespace-only reason, an unknown leave_type or role, and a date range that contains no Monday-to-Friday day.
- State conflicts return 409 {"detail": "..."}: deciding on a request that is not Pending, and approving an annual request whose working_days exceeds the employee's remaining balance (the message names the remaining balance); sick requests are never blocked by balance.
- All IDs are canonical lowercase hyphenated UUIDv4 strings generated by the server; clients never supply an id, full_name is stored and returned with its original casing and is not unique, and role, leave_type and status are accepted case-insensitively but stored and returned lowercase as employee|manager|hr_admin, annual|sick and pending|approved|rejected.
- No list endpoint pages in v1: every list returns all matching rows as a JSON array with no limit, offset, cursor or envelope, which is acceptable at the tens-of-users scale this app targets.
- Default order is deterministic per list: /users/active and /admin/users by full_name ascending case-insensitively then id; /leave-requests/mine, /notifications and /admin/audit-log by created_at descending then id descending (newest first); /leave-requests/pending by created_at ascending (oldest first) so the longest-waiting request is first.
- All timestamps are stored in UTC (timestamptz) and serialised as ISO-8601 with a 'Z' suffix; all calendar dates are plain ISO yyyy-mm-dd strings with no time part or offset, and "today" and "the current year" are always computed from UTC now, never from a client-supplied or server-local time zone.
- working_days counts every Monday-to-Friday date from start_date to end_date inclusive, with Saturday and Sunday excluded, no half-days and no public-holiday list, and is computed server-side and stored at submission so later edits to the calendar never change it.
- A leave request counts against the calendar year of its start_date, so a request spanning 31 December into January deducts entirely from the earlier year's balance.
- has_overlap is computed once at submission as true when the new request's inclusive date range intersects any Pending or Approved request of the same employee; it is only a flag, never blocks submission, and is not recomputed when other requests are later decided.
- GET /balances/mine returns remaining_days = allocated_days (20 by default) + adjustment_days - approved_annual_days for the current UTC year, may go negative only through an HR adjustment, and auto-creates the missing leave_balances row with allocated_days 20 and adjustment_days 0 the first time a user's balance is read.
- PUT /admin/users/{id}/balance stores the adjustment needed to make remaining_days equal the requested new_remaining_days for that year (it does not change allocated_days), requires a non-empty note, and writes one audit_log row with the acting HR/Admin, action type and note.
- Sick-leave reason is returned as JSON null (the key is always present) to any viewer who is not the employee, the employee's current manager, or an HR/Admin; /calendar entries never carry a reason field for anyone, and annual-leave reasons are not stripped.
- Writes that succeed with no useful body (POST /notifications/{id}/read, DELETE /sessions/current) return 204 with an empty body and are idempotent, so marking an already-read notification read again still returns 204.
- audit_log rows are append-only: nothing in the API updates or deletes one, and every submission, approve/reject decision (with its comment) and balance adjustment writes exactly one row carrying actor_user_id, action_type, created_at and a jsonb detail.
- Tests build every user, session, leave request and balance through the HTTP API only, signing in first as the HR/Admin user the backend seeds at startup and then creating what they need via POST /admin/users; no test reads or writes PostgreSQL directly or relies on migration-seeded demo rows.
- Each test creates its own users with names made unique per test (for example a uuid4 suffix) and asserts only on rows it created, because the suite shares one database between tests and never truncates tables between them.
